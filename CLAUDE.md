# CLAUDE.md - iWordle (Retro68 / Carbon, Mac OS 9 + Mac OS X + System 7 + Windows)

## Project Overview
This repository contains a native Classic Mac OS / Carbon Wordle clone built for PowerPC and 68k hardware, shipped as **five separate builds**: Mac OS 9 (via Retro68, also Mac OS 8.6 with CarbonLib), Mac OS X 10.4–10.14 (Carbon, a PowerPC + Intel Universal Binary via a real Apple SDK cross-compiler plus clang/ld64 for the i386 half), System 7.x / Mac OS 8 on 68k (via Retro68's m68k toolchain), modern macOS 11+ on Intel and Apple Silicon (Cocoa, built on a macOS runner), and Windows 3.1 (Win32s) / 95–ME / NT 3.51–XP on x86 (via Open Watcom 1.9). They cannot be combined into one "fat" binary — Mac OS 9 uses PEF/CFM, the Mac OS X builds use Mach-O, System 7 is a 68k application and Windows is a PE executable, different executable container formats (and, for System 7 and Windows, different CPUs).

- `src/core/` — the portable C99 game engine, shared by all platforms, with no Mac Toolbox/Carbon headers at all.
- `src/platform/macos9/` — Mac OS 9 front end, built via `.github/workflows/build.yml` inside the `ghcr.io/autc04/retro68` Docker image, styled with the authentic **Mac OS 9.2 Platinum Theme**.
- `src/platform/system7/` — System 7 front end for 68k Macs, built via `.github/workflows/build-system7.yml` inside the same `ghcr.io/autc04/retro68` Docker image but with the m68k toolchain (`CMakeLists.txt` branches on `CMAKE_SYSTEM_NAME`: `Retro68` selects this front end, anything else the Mac OS 9 one). Reuses `src/platform/macos9/icons.r`. Test rig: System 7.1 on a MAME-emulated Macintosh SE/30.
- `src/platform/macosx/` — Mac OS X front end, built via `.github/workflows/build-macosx.yml` with a `powerpc-apple-darwin8-gcc` cross-compiler against Apple's real `MacOSX10.4u.sdk`, styled with genuine Aqua chrome. Retro68 is only used there for its `Rez` tool (resource compilation), not the compiler/runtime.
- `src/platform/cocoa/` — modern macOS (11+) front end for Intel and Apple Silicon, built via `.github/workflows/build-macos.yml` on `macos-latest` with `clang` as one Universal 2 binary. A single Objective-C file (`main.m`), ARC, AppKit only, no nibs.
- `src/platform/win32/` — Windows front end, built via `.github/workflows/build-win32.yml` on `ubuntu-latest` with Open Watcom 1.9 (`open-watcom/setup-watcom`), invoking `wcc386`/`wrc`/`wlink` directly (no CMake). Two 32-bit PE EXEs from the same objects: `IWORDLE.EXE` (marked 4.0) for 95 / NT 4 through Windows 11, and `IWORD31.EXE` (marked 3.10) for Windows 3.1 with Win32s and NT 3.51. The icon is generated in CI from `src/platform/macos9/icons.r` by `tools/mac_icon_to_ico.py`. Test rig: Windows 3.11 (Win32s, in 86Box), 95/98/ME, NT 4/2000 and XP VMs (NT 3.51 is a supported target but untested, so its constraints must be right by construction).

## Build & Test Commands
Nothing is built locally — see the five GitHub Actions workflows above. `mkdir build && cd build && cmake .. && make` (Mac OS 9, inside the Retro68 Docker image) is what CI runs (System 7 does the same with the m68k toolchain file); the Mac OS X build needs Apple's non-redistributable SDK, so it only runs in CI; the Windows build calls the Open Watcom tools directly from its workflow; the modern macOS build runs `clang` on GitHub's `macos-latest` runner.

## Technical Guidelines & Constraints (all platforms)
1. **Target Environment:** Classic Mac OS / Carbon targeting PowerPC (G3/G4) architectures — Mac OS 9.x via Retro68, Mac OS X 10.4–10.14 via a real Apple SDK (Universal: PowerPC + i386). (System 7 is the exception: 68k, classic Toolbox — see below.)
2. **Color Palette:**
   * Active Tile Background: Crisp white (`#FFFFFF`) with dark gray inset borders (`#333333`).
   * Correct Letter: Forest Green (`#6AAA64`).
   * Misplaced Letter: Golden Yellow (`#C9B458`).
   * Absent Letter: Dark Slate Gray (`#787C7E`).
3. **Event Loop:** Handle window dragging, updating (`updateEvt`), and keyboard/mouse clicks using low-level Mac OS Event Manager routines (`WaitNextEvent`, `keyDownEvt`).
4. **Code Style:** Standard C99 compatible with Mac Toolbox headers (`<Quickdraw.h>`, `<Windows.h>`, `<Controls.h>`, `<Events.h>`). Avoid modern standard libraries that require heavy runtime environments.

## Mac OS 9 specifics
Follow Mac OS 9 Platinum guidelines strictly. Use crisp monochrome bevels (`FrameRect`, `PaintRect`), Geneva typography (`TextFont(geneva)`), and native window borders (`documentProc`/`noGrowDocProc`).

## Mac OS X specifics — no hand-drawn UI, ever
**Standing rule, learned the hard way:** every window and dialog must be built from real native Carbon controls — `CreateStaticTextControl`, `CreateEditUnicodeTextControl`, native buttons, `SetThemeWindowBackground` for backgrounds — never `DrawString`, `DrawThemeTextBox`, raw ATSUI, or any hand-painted background. This isn't a style preference: an extended debugging arc (see git log around the About/Ranking/message-box UI work) tried every hand-drawn approach and each one rendered subtly wrong (wrong font, missing antialiasing, wrong weight) in ways specific to this cross-compiled toolchain — only genuine native controls rendered correctly, since the OS does the rendering, not this code. If you're tempted to hand-draw text or a background here, use a native control instead.

A few non-obvious things this codebase learned about that toolchain, in case they come up again:
- `GetFNum()`-by-name font resolution and `DrawString()` don't reliably render right — go through `CreateStaticTextControl`/`UseThemeFont()` instead.
- `GetNewDialog()`/`ModalDialog()`'s window doesn't respect `SetThemeWindowBackground()` — use a plain `WIND` (`GetNewCWindow` + a small `WaitNextEvent` loop) for anything that needs a correct native background, not a DLOG/DITL dialog.
- `DisposeControl()` doesn't reliably remove a control from its window — when rebuilding dynamic content (e.g. a table after a "Clear" action), tear down and recreate the whole window rather than trying to dispose/recreate individual controls in place.
- `ChangeWindowAttributes(win, 0, kWindowResizableAttribute)` removes functional resizing but a `documentProc` window's frame still renders grow-box chrome regardless — use `noGrowDocProc` at the resource level for any window that should never be resizable. The main window is the deliberate exception: it is now intentionally a resizable `zoomDocProc` (see "Resizable main window" below), so its grow chrome is wanted.
- Classic `icns` `it32`/`ih32`/`il32`/`is32` icon RGB data must be PackBits-compressed, not raw, or real Icon Services renders it as garbage.
- **Universal Binary:** the cross-compiler images' SDKs have their i386 slices stripped, so the Intel half links against a full `MacOSX10.4u.sdk` from `phracker/MacOSX-SDKs` (download pinned by SHA-256 in `build-macosx.yml`), compiled with the image's `clang -target i386-apple-darwin8` and linked with cctools' `ld64` directly, then `lipo`'d with the gcc-built PowerPC half. Code in `src/platform/macosx/` must compile under both gcc (PowerPC) and clang (i386).

## System 7 specifics
**Target:** 68k (68030), not PowerPC, built with Retro68's m68k toolchain (`/Retro68-build/toolchain/m68k-apple-macos/cmake/retro68.toolchain.cmake`). Guidelines 1 and 4's PowerPC/Carbon wording does not apply here — this is the classic Toolbox only, with no Carbon and no Appearance Manager. Do not use `GetPortBounds`, `SetPortWindowPort`, `GetQDGlobalsScreenBits`, `GetWindowPort`, `ChangeWindowAttributes`, `EnableMenuItem`, `kControlEditTextProc` controls, `SetKeyboardFocus` or `HandleControlKey`; use `SetPort(w)`, `w->portRect`, `qd.screenBits.bounds`, `EnableItem`/`DisableItem` and Dialog Manager EditText instead. The Toolbox must be initialized by hand (`MaxApplZone`, `MoreMasters`, `InitGraf`, `InitFonts`, `InitWindows`, `InitMenus`, `TEInit`, `InitDialogs`, `InitCursor`).

- **Screen:** the test machine's built-in display is 512×342 and **1-bit**, with a 20px menu bar, so every window and dialog must fit that. The main window is 304×298 at 100% (the bottom keyboard row, Enter + 7 letters + Delete, sets the width; the bottom 20px are reserved for the grow box plus a gap) and resizable, see the resizable-window section below.
- **Color vs. mono gotcha:** the SE/30 ROM *has* Color QuickDraw but its screen is 1-bit, so never choose color from `gestaltQuickdrawVersion` alone. Use the color palette only if Color QD is present **and** the main device's pixel depth is at least 4, and re-check at each full redraw. The monochrome path uses classic 1-bit idioms: black fill for correct, gray pattern plus a white badge for present, and a gray-dimmed tile for absent.
- **Fonts:** Chicago (system font) and Geneva only — no Charcoal.
- **Stats file:** lives in the **Preferences** folder via `FindFolder` (there is no Application Support folder on System 7.1), flat, named `iWordle Stats`, type `STAT`, creator `WRDL`, same `WordleStatsBook` dump as the other builds.
- **Performance:** the CPU is slow (16 MHz) with no double buffering, so redraw only the affected tiles on a keystroke and do full redraws only on submit, new game and update events.
- **Dialogs:** unlike Mac OS X, the classic Dialog Manager (`DLOG`/`DITL` + `ModalDialog`, `ALRT` + `NoteAlert`) is the *right*, native tool on System 7 — the OS X "no DLOG/DITL" rule does not apply here.
- **Desk accessories:** the Apple menu lists the system's `DRVR` resources (`AppendResMenu` + `OpenDeskAcc`), clicks in system windows go to `SystemClick`, and a standard Edit menu is routed to `SystemEdit`.
- **Palette:** the CLAUDE.md color palette applies on color displays only; monochrome displays use the 1-bit scheme above.

## Modern macOS specifics
- **AppKit + ARC, no nibs/xib/storyboards, no Swift.** `src/core/` is compiled as plain C alongside `main.m`. Deployment target is macOS 11.0 (first Apple Silicon release). The OS X "no hand-drawn UI" rule applies to dialogs here too: messages, the name prompt and Ranking use `NSAlert` sheets and a real `NSTableView`; only the board tiles are custom-drawn. The About box is a custom 280x230 `NSWindow` mirroring the OS X build's (same label tops, fonts, no OK button; closes with the close box, Cmd-W, Esc or Return).
- **Universal 2 + ad-hoc signing:** CI builds `-arch x86_64 -arch arm64` and runs `codesign --force --deep -s -` (arm64 refuses unsigned code). It is not notarized, so users right-click → Open the first time.
- **System appearance (light/dark):** the appearance is not forced. The state colors (#6AAA64, #C9B458, #787C7E) are fixed, but the empty-tile fill/border/letter are dynamic colors (`colorWithName:dynamicProvider:`): #FFFFFF/#333333/#333333 in light mode, #121213/#565758/#FFFFFF in dark mode; the window background is `windowBackgroundColor`.
- **On-screen keys are real `NSButton`s** (subviews of the board view, `refusesFirstResponder`, frames set in `layout` from the scaled layout helpers), so each OS draws its own button (Aqua, or Liquid Glass when built with the macOS 26 SDK). Guessed letters set `bezelColor` to the palette color with a white `attributedTitle`. The bezel style is `NSBezelStyleFlexiblePush` on the macOS 26 SDK and `NSBezelStyleRegularSquare` (same value) before it, chosen with an `#if` on `__MAC_OS_X_VERSION_MAX_ALLOWED`. CI selects the newest installed Xcode; the deployment target stays 11.0, so any newer API needs `@available`.
- **Layout:** same design units as the OS X build (502 wide, `LAYOUT_H` 544 plus the 14 margin = 558 tall), one aspect-preserving scale, 60% minimum; there is no grow box, so no grow band.
- **Stats file:** `~/Library/Application Support/iWordle/iWordle Stats`, a flat `WordleStatsBook` dump, not shared with the old builds.

## Windows specifics
**Target:** 32-bit x86, ANSI Win32, built with Open Watcom 1.9 (a C89 compiler, so `src/core/` and `src/platform/win32/` stay C89: declarations at the top of each block, `/* */` comments only, no `//`, no `stdint`/`stdbool`, no `long long`). Guidelines 1 and 4's PowerPC/Carbon/Toolbox wording does not apply here.

- **NT 3.51 is the compatibility floor.** The same objects are linked twice: `IWORDLE.EXE` with `runtime windows=4.0` (95/NT 4 and later give 4.0 programs the 3D look and XP+ themes; 3.10-marked programs are drawn flat) and `IWORD31.EXE` with `runtime windows=3.10` (NT 3.51 refuses images whose subsystem version is 4.0; also the Win32s build). Both obey the NT 3.51 API floor and may statically import only **KERNEL32, USER32 and GDI32**. CI audits the import table and fails the build on any other DLL, on any forbidden API, and (once `src/platform/win32/allowed-imports.txt` exists) on any import not listed in it.
- **Win32s target (Windows 3.1 / 3.11 with Win32s 1.30c).** The same EXE must load there, so: no static imports beyond KERNEL32/USER32/GDI32; COMCTL32 is loaded dynamically (`LoadLibrary` + `GetProcAddress` for `InitCommonControls`, never `FreeLibrary`d, so XP's comctl32 v6 stays loaded for theming); relocations are required (never link with `option norelocs`; CI checks for a `.reloc` section); and a `LoadLibrary` failure is checked as `(UINT)h < 32` as well as NULL, since Win32s reports errors that way.
- **Forbidden APIs** (95/NT 4+ or later): `LoadImage`, `DrawEdge`, `DrawFrameControl`, `DrawState`, `RegisterClassEx`/`WNDCLASSEX`, `GetSysColorBrush`, `GetMenuItemInfo`/`SetMenuItemInfo`, `CheckMenuRadioItem`, `TrackMouseEvent`, anything from SHELL32, `GetFileAttributesEx`, `GradientFill`/`AlphaBlend`/`TransparentBlt`, `SetWindowLongPtr`, `InitCommonControlsEx`. Use only the Win 3.x system colors (`COLOR_BTNFACE`, `COLOR_BTNSHADOW`, `COLOR_BTNHIGHLIGHT`, `COLOR_BTNTEXT`, `COLOR_WINDOW`, `COLOR_WINDOWTEXT`, `COLOR_WINDOWFRAME`) and build brushes with `CreateSolidBrush(GetSysColor(...))`. `SystemParametersInfo(SPI_GETWORKAREA)` may be called but fails on NT 3.51, so fall back to `SM_CXSCREEN`/`SM_CYSCREEN`.
- **ANSI only:** never define `UNICODE`/`_UNICODE`; Windows 95 has no working wide-character APIs.
- **Screen / resizing:** the layout is designed at 356×398 so the window fits a 640×480 Windows 95 desktop with a taskbar. The window is resizable (`WS_OVERLAPPEDWINDOW`): every rect and font is scaled from those design units by one aspect-preserving factor (`gScale`, per mille, set on `WM_SIZE`) and centered, with a 60% minimum via `WM_GETMINMAXINFO`. Layout helpers return already-scaled rects, so hit-testing and invalidation follow automatically.
- **Dialogs:** unlike Mac OS X, native `DIALOG` resources in `iWordle.rc` plus `DialogBoxParam` are the *right* tool here (`DS_MODALFRAME | DS_3DLOOK`, `MS Sans Serif` 8), and menus are standard resource menus. XP theming comes from the `iWordle.manifest` (comctl32 v6) plus `InitCommonControls`.
- **Stats file:** `IWORDLE.DAT` next to the EXE (8.3 name, found via `GetModuleFileName`), a flat dump of `WordleStatsBook`; saving fails silently on read-only media. It is not shared with the Mac builds.

## Resizable main window (all builds)
- The main window is resizable and zoomable, and the tiles, keys and fonts scale with it. The layout `#define`s (`TILE_SIZE`, `KEY_SIZE`, `KEYBOARD_TOP`, ...) are "design units", the layout at 100%, with `DESIGN_W`/`DESIGN_H` the design content size. `UpdateLayout(contentW, contentH)` sets `gScale` (per mille, aspect preserved) and a centering `gOffsetX`/`gOffsetY`; the content can't shrink below `MIN_SCALE` (60%) of the design size. The layout helpers (`GetTileRect`, `GetLetterKeyRect`, `GetBackspaceKeyRect`, `GetEnterKeyRect`) return already-scaled rects via `ScaleRect`, so painting, hit-testing and partial redraws use them as-is: never use a layout constant directly outside those helpers. Main-window font sizes go through `ScaleLength` (floor 7); other windows don't scale.
- On the Mac builds the vertical scale is computed from `LAYOUT_H` (the design-unit bottom of the keyboard) within `contentH - GROW_BAND`, where `GROW_BAND` is the 15px grow box plus a 5px gap, so no key ever touches the grow box at any scale or window shape. Windows has no grow box and scales the whole client area.
